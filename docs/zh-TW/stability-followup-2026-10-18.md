# HTTP／JMS 穩定性追加驗證

[English](../stability-followup-2026-10-18.md) · [前一階段](long-running-stability-2026-10-18.md)

後續實驗：[SQLite 請求紀錄 JDBC 寫入比較](request-log-jdbc-experiment-2026-10-18.md)。

[大訊息容量檢視](capacity-and-framework-review-2026-10-18.md) 補充後來發現的持續寫入備份問題、修正與 512 MiB 保留量驗證。

本輪功能提交為 `97aa408`，磁碟重試邊界修正為 `517578e`；均在 `codex/long-running-stability`，未開 PR 或合併。
目標是維持原有功能，查清故障影響、限制資源累積，並以連續 10 分鐘取代更長的觀察。
本輪沒有修改 JMS provider、來源 listener 配置、ACK、交易或重試政策。

## 1. JMS 慢下游的影響範圍

1. **原本問題**：各目標的鎖已分開，但同一來源 queue 仍共用 listener pool。全部工作者都在等慢下游時，正常目標也要排隊。
2. **怎麼改善**：補上真實外部 Artemis 的邊界測試，明確區分鎖隔離與來源容量；本輪沒有強行改成另一種排程或縮短等待。
3. **實測效果**：來源固定 2 個工作者時，占住 1 個，正常 JMS 與 HTTP 仍在 5 秒／2 秒門檻內回覆；占滿 2 個，正常 JMS 在 300 ms 內無回覆，釋放後所有內容、correlation ID 正確，來源 queue 與處理中工作歸零。含鎖隔離與交易失敗重送的 13 項針對性測試通過。
4. **代價與限制**：證明的是現有容量邊界，**尚未提供同一來源 queue 內各目標的強隔離**。保留原有交易政策；實際 TIBCO EMS 因無可用授權套件，仍未驗證。

## 2. 連續負載與自然 GC

1. **原本問題**：原本分輪負載後閒置、再要求 GC，適合比較保留量，卻不能代替不間斷流量。
2. **怎麼改善**：觀察工具新增 `--continuous`，正式流量不分段，基準、負載與結束均不要求 GC。以一分鐘視窗、自然 GC 與每分鐘 NMT 摘要檢查七項資源；缺資料不算通過。
3. **實測效果**：修改前的基準產物完成 600.036 秒、120,000 筆正確請求；HTTP／JMS 各半，包含真實轉發。七項成長門檻通過，0 記錄丟棄、0 ERROR／OOM、50 次備份成功。自然 GC 後 Heap 視窗差約 +0.9 MiB、RSS 約 +5.0 MiB。最終產物結果另列於下方。
4. **代價與限制**：10 分鐘能找出本負載下的明顯異常，不能證明數週無洩漏。Young GC 後的 Heap 不是完整存活量；NMT 與監控也有成本。本工具量測穩定性，不是最大吞吐量。

## 3. 磁碟空間與資料庫故障

1. **原本問題**：暫存檔雖有待寫入容量上限，卻未依所在磁碟的可用空間提早停止新寫入；主資料庫鎖住時也需要驗證恢復與重複寫入。
2. **怎麼改善**：預設在 request-log spool 所在磁碟預留 512 MiB。既有背景 writer 最多每秒查一次，請求與監控只讀快取狀態；不足或查詢失敗時拒絕尚未嘗試的新批次，背景持續檢查，恢復後重新接單。已嘗試、結果尚未確認的批次保留原有重試流程，不能改稱未寫入而讓呼叫端重送。另補真實 SQLite 寫鎖整合測試。
3. **實測效果**：注入空間不足／探測失敗後停止新寫入，沒有新請求時也能偵測恢復。真實主資料庫鎖住期間，5 筆 HTTP 與 5 筆 Artemis JMS 正常回覆；解鎖後連同 2 筆暖機共 12 筆紀錄完整、無重複，佇列歸零。另以先失敗、後修正通過的測試確認低空間不誤報已嘗試批次未寫入；相關 41 項測試通過。
4. **代價與限制**：空間不足時比原本更早停止新記錄。已開始的有限批次仍可重試，以保留既有寫入結果契約。預設非同步模式維持有上限的丟棄策略；選用嚴格模式時，沿用既有失敗／重送行為。這不是整顆磁碟的硬配額，無法替其他程式預留空間；本次安全注入低空間，沒有真的填滿磁碟。

設定 `ECHO_REQUEST_LOG_SPOOL_MIN_FREE_BYTES=0` 可停用預留檢查。監控列出預留量、已探測可用量、是否阻擋與探測失敗次數。

## 4. 分清記錄保留與失敗

1. **原本問題**：舊 `dropped` 合計混在一起，無法直接分辨保留政策跳過、尖峰緩衝淘汰與未確認寫入，容易把設計取捨誤判成服務異常。
2. **怎麼改善**：保留原合計，管理 API 與中英文畫面新增保留跳過、緩衝滿淘汰、寫入未確認、其他丟棄，以及儲存重試次數。只用固定數量的累計計數器，不增加每筆歷史。
3. **實測效果**：保留跳過 7 筆、緩衝淘汰 16 筆、未確認寫入 1 筆與其他拒絕各有獨立斷言；儲存中斷會累計重試。相關 156 項後端與 15 項監控前端測試通過。
4. **代價與限制**：這是觀測改善，沒有把預設記錄策略改成每筆必存。未確認寫入可能稍後提交，不等於確定遺失；重試是嘗試次數，不是丟失筆數。並行取樣的計數不保證同一瞬間完全對齊。

## 5. 回收閒置 HTTP 工作者

1. **原本問題**：原生 HTTP 工作執行緒在尖峰後永久保留，連帶保留 JVM thread stack 等資源，即使之後完全閒置。
2. **怎麼改善**：預設閒置 60 秒後回收；下一筆工作按需重建。忙碌工作不會因這個計時被中斷，容量、緩衝上限及 JMS 執行緒不變。監控另列實際存在的原生工作者數。
3. **實測效果**：打包後 HTTP 逐筆核對負載，32 個工作者於 65 秒閒置後降為 0；下一筆內容正確，約 2.48 ms 完成，重建 1 個工作者。NMT thread committed 約 6.91 → 3.33 MiB。28 項針對性測試通過，包含忙碌工作跨過閒置期限仍完成。
4. **代價與限制**：閒置後第一筆有建立執行緒成本；不保證 RSS 立刻下降，也不代表收回所有程序記憶體。`ECHO_HTTP_NATIVE_WORKER_IDLE_TIMEOUT_SECONDS=0` 可恢復原本不回收的行為。

## 6. HTTP 轉發尾端延遲

1. **原本問題**：基準混合測試中 HTTP 轉發 P99 約 46 ms，直接打測試下游也出現約 44 ms 的典型延遲，需要先拆開下游與 Echo 成本。
2. **怎麼改善**：同一份 Echo 產物，僅切換測試用 JDK HTTP 下游的 `TCP_NODELAY`，保留原模式供重跑；不改產品轉發核心。再以獨立 Node 下游與 WireMock 作相同轉發測試。
3. **實測效果**：16 KiB、每組 250 筆核對樣本，直接下游 P99 為 48.20 → 5.14 ms，經 Echo 為 58.03 → 9.27 ms。這顯示測試下游 TCP 設定是主要因素；**不能將差值宣稱為 Echo 產品加速**。WireMock 對照另列於下方。
4. **代價與限制**：最後混合測試預設使用修正後下游，且工具提交 `b0d4bf3` 明確指定 HTTP/1.1；舊工具會嘗試 h2c 升級，可能走 Servlet。因此新舊延遲不能當成產品修改前後的純 A/B。加 `--downstream-nagle` 可保留舊測試下游設定。250 筆診斷樣本僅用來定位，不作容量結論。

## 最終量測與重跑

最終產物 `517578e` 完成 **600.060 秒不間斷負載、120,000 筆正確回應**，HTTP／JMS 各 60,000 筆。暖機另計 18,000 筆。七項資源成長門檻全部通過，0 ERROR／OOM／非預期退出，0 記錄丟棄與儲存重試。結束後請求、緩衝、寫入佇列均排空，下游只剩既定服務 queue，沒有暫時 queue 殘留。

全程未要求 GC；正式負載觀察 209 次自然 GC，含暖機共封存 246 筆、過期清除 232 筆。正式負載中 8 條停滯上傳均已由伺服器回收，暖機另有 48 條。包含暖機與排空的整段流程，備份成功 50 次、失敗 0，清除 47 份舊備份，最後保留 3 份、約 54.5 MiB。

### 連續測試重跑

連續測試使用獨立程序及資料庫，不連公司 ESB。Linux／JDK 17、G1、Heap 384 MiB，HTTP 2 個 I/O／8 個工作者，JMS 2–4 個 listener；每秒合計 200 筆、16 KiB 資料，6 × 15 秒暖機後正式負載 600 秒。

```bash
./gradlew bootJar memoryObservationFixtureJar
python3 scripts/test-memory-observability.py \
  --jar build/libs/echo-server-0.0.0-SNAPSHOT.jar \
  --output build/observations/continuous-10min \
  --continuous --cycles 1 --seconds 600 --rate 200 \
  --warmup-cycles 6 --warmup-seconds 15 \
  --http-stalls --backup-maintenance
```

Windows 使用 `gradlew.bat` 與 `python`，`--java` 可指定完整 JDK 的 `java.exe`；輸出目錄須尚不存在。詳見 [GC 觀察指南](gc-observability.md)。原始日誌、JAR、JVM 摘要與時序檔留在 Git 外；本報告只保留文字摘要。

原始測試工作目錄為 `stability-next-six-20261018`：`continuous-10min` 是修改前基準，`continuous-10min-accepted` 是最終驗收；`forward-wiremock`、`forward-diagnosis`、`http-idle-v2` 分別保存轉發比較、TCP 診斷與閒置回收。兩次預跑中斷保留原因與未通過狀態，不計入正式驗收；`reserve-retry-red.log`／`reserve-retry-green.log` 與 `full-check-final.log` 保留回歸證據。
