# HTTP／JMS 長期運作的穩定性補強

[English](../long-running-stability-2026-10-18.md)

目標是慢客戶端或下游故障時仍能服務，工作結束後資源能回到基準。有限次測試無法證明
永遠沒有洩漏。以下以 Linux／JDK 17 比較 main `3ede241` 與本次實作；Windows CI 驗證功能相容性。

## 1. 停滯上傳

1. **原本問題**：有宣告長度的本文以阻塞方式讀取；逾時關閉連線後，名額雖歸還，工作執行緒
   仍卡在 `awaitReadable`。32 個工作執行緒遇到 32 個停滯上傳時，設定 1 秒逾時，正常小請求
   等超過 6 秒仍未回應。
2. **怎麼改善**：使用 Undertow 有容量上限的非阻塞接收，同時處理宣告長度與 chunked。
   每筆請求的期限由該連線的 I/O 執行緒計時，涵蓋上傳、排隊、pipeline、延遲與回應傳送；
   過期排隊工作會移除。監控另列實際忙碌工作執行緒。
3. **實測效果**：相同 32 個工作執行緒的故障測試，小請求約 2.6 ms 回應；客戶端保持連線時，
   逾時後工作執行緒、名額、緩衝與佇列均歸零。兩種本文格式都有整合測試。
4. **代價與限制**：每筆原生請求多一個期限及取消處理。已開始的任意 CPU／資料庫工作無法安全
   地強制終止；multipart、HTTP/2、SSE 等既有 Servlet fallback 維持各自處理方式。

## 2. 停止讀取回應的客戶端

1. **原本問題**：pipeline 完成後就取消逾時計時。容量設 4 的測試中，4 個停讀的 4 MiB 回應
   在 4.5 秒後仍占滿名額及約 48 MiB 緩衝預留額度，小請求收到 503。
2. **怎麼改善**：期限持續到傳送完成；本文未收完或回應已送出部分資料時，逾時關閉連線。
   本文完整且回應尚未開始時，維持 504 回應。
3. **實測效果**：期限設 1 秒時，約 1.1 秒觀察到 4 筆名額與預留量全部釋放；此時測試客戶端仍
   保持連線，小請求正常回 200。延遲、容量、大小限制、TLS、斷線與追蹤回歸測試保留。
4. **代價與限制**：一般下載也須在期限內完成，因此刻意很慢的下載需調整總期限；明確要求 SSE
   的請求仍走既有路徑。

### 正常 HTTP 吞吐檢查

固定回 `ok`、關閉請求記錄、Heap 384 MiB、2 個 I/O 與 8 個工作執行緒。4 個全新 JVM
依前→後→後→前執行，各暖機 15 秒，再以併發 16／64 各量 15 秒。
Echo 固定 3 個 CPU，驗證回應的 wrk 固定另一個 CPU；沒有並行建置或其他負載產生器。
逐筆核對狀態與本文，沒有 socket、逾時或內容錯誤。

| 併發 | 原本平均 req/s | 修正後平均 req/s | 變化 | 原本各輪 P99 平均 | 修正後各輪 P99 平均 |
|---|---:|---:|---:|---:|---:|
| 16 | 90,301 | 93,691 | +3.8% | 1.66 ms | 1.63 ms |
| 64 | 108,913 | 108,773 | -0.1% | 2.55 ms | 2.19 ms |

每個版本只有兩次觀察，不能推論所有負載都會變快，也不是與 WireMock 比較。P99 為各輪
百分位的平均，不是合併樣本的百分位。本次重點是保留正常效能並修正故障時的行為。

## 3. JMS 下游連線等待

1. **原本問題**：回覆逾時只在 `receive` 開始計算。下游只接受 TCP、不完成 broker 握手時，
   設 1 秒的回覆逾時，3 秒後仍卡在建連線。
2. **怎麼改善**：provider 加入可選的轉發專用 factory 建立路徑。預設
   `echo.jms.forward.bounded-waits-enabled=false`，保留原本連線、重試與 failover 設定。
   明確開啟後，Artemis 才限制 TCP、broker call 與
   failover 等待，保留原本更短的限制，失敗後由 forwarder 在下一次請求重建 client。
   來源接收設定保留；管理頁連線測試也套用轉發限制。
3. **實測效果**：明確開啟限制時，legacy、default、具名目標都測試黑洞連線失敗、相同地址恢復成真實 broker 後
   成功轉發，且無殘留 TemporaryQueue。設定 1 秒時，包含故障與恢復的整個測試約 1.18～1.29 秒。
4. **代價與限制**：預設仍保留原本可能很長的等待；開啟後較長的轉發 URI 重試設定會被收斂，
   原本可等到重連／failover 成功的請求可能提早失敗。既有錯誤回覆流程正常完成來源交易，
   不會自動保留該筆訊息重送。各階段有限期但整段流程可能超過一個
   逾時值。逾時不代表下游未收到訊息。EMS 僅設定每個 factory 的連線嘗試，不改全域 request
   timeout；缺少授權 client，未完成 EMS 的 send／ACK 與 failover 實機驗證。
   同一來源 queue 中，慢工作仍可能占滿 listener，尚未提供強隔離。須用實際 ESB 驗證後才開啟。

詳見 [JMS 契約](../jms-performance-and-correctness.md)。

## 4. 舊回應的 housekeeping

1. **原本問題**：依 ID 刪除會逐筆載入完整回應，再逐筆刪除，全部包在一個交易。
   此建置中，光加 `LAZY` 註記仍會讀取 body。
2. **怎麼改善**：每批只取最多 100 個 ID，直接在資料庫刪除；每批重新確認過期時間與 HTTP／JMS
   引用，提交時一起發布快取失效。工作開始的最大 ID 作為邊界，讓單次工作有限。
3. **實測效果**：ABBA 比較刪除 500 筆、每筆 64 KiB 的舊回應，先以 100 筆暖機。
   平均時間約 149.3 → 41.6 ms，減少約 72%；載入的 Response 實體 500 → 0；整次清理的
   SQL prepared statements 1,004 → 14。符合條件的資料全部刪除。另有引用／展延保護、後段失敗
   回滾與再次執行的 SQLite 測試。
4. **代價與限制**：整次工作不再是一個原子交易；後段失敗時，前面已成功的批次保留提交成果，
   下次處理剩餘資料。更多提交與快取事件，換取有邊界的回應清理記憶體與較短的連續寫入占用。
   規則／Scenario 清理仍使用原有操作。

## 5. 重複重建規則快照

1. **原本問題**：Windows CI 找到兩個讀者同時判斷過期的競態。第一個完成更新後，延遲的
   讀者仍根據舊快照的判斷取得空出的重建名額，再多查一次資料庫。
2. **怎麼改善**：取得重建名額後，再確認最新快照是否仍需更新；不需要時釋放名額，並接手
   期間到達的新變更，避免漏掉更新。平常讀取新鮮快照的路徑保留。
3. **實測效果**：可控制兩個讀者執行順序的測試，在修正前固定失敗（建立 3 次），修正後為
   2 次（首次建立＋必要更新）。這是該競態下的減少，不是整體吞吐測量。
4. **代價與限制**：只有取得重建名額時多一次新鮮度檢查；平常讀取不增加。重建時先回舊快照、
   變更序號、更新等待與失敗重試維持原有契約。

## 負載與閒置觀察

Linux／JDK 17 完成 6 輪重新連線暖機及 10 輪、每輪 60 秒的正式測量，共核對 60,000 筆
HTTP／JMS 請求。80 條停滯上傳連線都在測試端仍保持連線時回收；請求記錄丟失、JMS 轉發、
回覆與暫存佇列清理失敗均為 0。閒置後 GC 的 heap 由基準 99.37 MiB 到第 10 輪 93.20 MiB；
封存 148 筆 GC 事件，程序內有期限的紀錄過期移除 139 筆。

七項資源序列均通過既有成長門檻，不代表使用量完全不增加：前後視窗比較，non-heap 約增加
9.2 MiB、RSS 約增加 37.9 MiB、JVM 執行緒增加 3。整次約 16 分鐘，只在閒置且資源排空後
要求 GC，不能證明永不洩漏或 ESB 可全年無休穩定運作。

本次凍結的產物使用加入相容性開關前的 Artemis 等待限制；結果用於此模式及 HTTP 資源修正，
不是最後預設政策產物的量測，也不是授權 EMS 的實機結果。最後的預設政策另以轉發、連線測試
及來源政策回歸測試驗證。

## 重跑驗收

JDK 17 執行整合測試與 `check`，Windows 也需通過。依 [GC 觀察指南](gc-observability.md)
啟動獨立測試工具，在指令後加上 `--http-stalls --warmup-cycles 6 --warmup-seconds 15`。
預設 10 輪、每輪 60 秒，包含正常 HTTP／JMS、記錄寫入、反覆停滯上傳、暫時佇列清理、
實際忙碌執行緒、GC 過期與閒置後資源趨勢。小量或特定負載的洩漏仍需部署規格的更長測試。

原始量測檔保存在原始碼庫外；部署效能測試可沿用 `scripts/bench`。

## 同一分支追加的維運修正

### JMS 目標隔離

1. **原本問題**：建立 factory、淘汰閒置或舊版 client 時持有所有目標共用的 map 鎖；一個 provider 卡住，可能讓另一個正常目標的第一筆請求也卡住。
2. **怎麼改善**：發布 client 前先保留使用權；共用鎖內只停止接單、移除舊 client，provider 的建立與關閉移到各自生命週期處理。共用鎖內不取得已發布 client 的 monitor。不增加 executor、不強制中斷，也不改 ACK、交易或重試政策。
3. **實測效果**：factory 建立、閒置淘汰、舊版關閉三種可控故障，修改前都超過 2 秒驗收門檻；修改後另一個 provider 仍被刻意卡住時就能完成回覆。JMS 回歸共 273 個測試、零失敗、6 個略過，包含實際 Artemis 交易、轉發、回覆隔離與回收。
4. **代價與限制**：factory 改為各 client 首次使用時建立，淘汰仍等待既有使用者完成。同一目標仍可能等待 provider，來源 listener pool 也尚未依目標分隔。替身驗證的是 Echo 的鎖，並非授權 EMS 實機或一般吞吐量測。

### 備份失敗後仍能清理

1. **原本問題**：只有新備份成功才清過期檔，且沒有容量／數量預算；目的地滿了時，新備份與清理可能一起失敗。
2. **怎麼改善**：每小時獨立清理，維護不重疊，複製前檢查容量及可用空間。預設保留 7 天、最多 10 GiB／100 份已完成備份，預留 512 MiB。保留最新有效備份，即使已過期；更新但損壞的檔案不取代它。沒有任何備份可驗證時，保留現有復原材料。不刪其他檔案、目錄或符號連結。
3. **實測效果**：14 個保留／容量測試加上原本 3 個備份測試，涵蓋來源不可用、注入空間不足後恢復、容量／數量清理、損壞備份、並行操作及 Windows 相容路徑。仍使用 online backup、完整性／外鍵驗證與原子發布。
4. **代價與限制**：容量可能縮短歷史；無法同時容納新備份與最後有效備份時拒絕複製。驗證增加維護 I/O；空間檢查無法替其他程序或資料庫後續成長保留磁碟。限制不包含其他檔案與強制終止殘留暫存檔。已驗證並發布的備份不因後續清理失敗而回報備份失敗。

### 存活與就緒探針

1. **原本問題**：容器只看管理統計 API 的 HTTP 狀態；JMS 重新連線時仍回 200，判斷存活也要額外讀取 DB 統計。
2. **怎麼改善**：標準 Actuator liveness 檢查存活，readiness 另檢查 DB、磁碟與既有來源 listener。只有兩個 GET 可匿名讀取，且只回狀態。停用額外開 JMS 連線的 indicator。Docker 使用 readiness、Java 直接作為 PID 1、Compose 預留 60 秒關閉；CI 可在開 PR 前手動對分支執行，包含容器停止／重啟測試。
3. **實測效果**：實際外部 Artemis 停止後 readiness 回 503、liveness 保持 200；重啟後 readiness 恢復 200 且 JMS 回覆正確。涵蓋匿名範圍、只回狀態、JMS 停用與 DB 故障映射。本機 JDK 17 完整建置通過 2,177 個測試、零失敗、6 個略過，另通過靜態分析。
4. **代價與限制**：readiness 沿用 datasource 逾時，liveness 不依賴 DB／ESB。listener 狀態不能辨識所有卡住的操作。Compose 只重啟已退出容器，無回應時自動重啟仍需以 liveness 判斷的監管程序。探針不強制中斷交易。

觀察工具加上 `--backup-maintenance`，每 15 秒備份 SQLite、獨立清理到最多 3 份／256 MiB，檢查保留容量並於閒置時驗證探針。沒有備份／清理完成，或有備份失敗，都不通過。這仍是有限時間回歸；長期驗收應使用部署規格跑 24～72 小時。

### 修改已使用的共用回應

1. **原本問題**：回應被使用過之後，在規則內改寫既有內容，資料庫已存新值，HTTP／JMS 卻可能持續回舊快取。JPA 比較時拿到同一個已被改過的物件，誤判內容沒變；原本 main 也能重現。
2. **怎麼改善**：比較拿到同一個物件時，保守清除該回應快取。保留提交前／後清除及跨實例通知；獨立傳入、只改描述的回應仍可沿用快取，交易請求不增加資料庫讀取。
3. **實測效果**：先確認兩條 HTTP 規則共用已快取內容、清空內容，以及真實 Artemis JMS 與 HTTP 共用回應的測試會失敗，再以相同測試確認修正。SSE 驗證、交易回滾與版本衝突仍納入驗收。
4. **代價與限制**：重新儲存同一個已載入物件，即使內容最後沒變，也可能清快取，下一次使用須重新載入。這是管理操作的成本，不是每筆交易額外檢查；實際 TIBCO EMS 仍未驗證。

### 備份排程與清理衝突

1. **原本問題**：30 分鐘混合觀察出現 3 次排程備份碰到清理鎖而被拒絕，後續排程雖恢復，但每天一次的備份可能因此漏掉一份復原點。
2. **怎麼改善**：排程等待維護鎖，取得後才製作已驗證的備份；等待可中斷。手動重複備份仍立即回報忙碌，清理仍跳過正在製作的備份，不增加執行緒池或重試佇列。
3. **實測效果**：確定性的真實 SQLite 測試先卡住清理、確認備份等待，釋放後檢查有效備份；另一個測試中斷等待者，再確認後續備份仍能成功。兩項測試在修正前均失敗。
4. **代價與限制**：等待占用一條背景排程執行緒，但不先占 JDBC 連線，也不占 HTTP／JMS 工作者。原維護作業多久完成，就可能等多久；關閉可中斷等待，實體儲存失敗仍明確回報。
