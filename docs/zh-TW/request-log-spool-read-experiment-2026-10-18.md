# 請求紀錄 JSON／spool 讀取實驗

[English](../request-log-spool-read-experiment-2026-10-18.md) · [前一輪 framework 分析](capacity-and-framework-review-2026-10-18.md)

這次改善背景搬運紀錄的成本；**不能宣稱 JMS 整體加速，也不能把十分鐘觀察寫成全部通過**。

1. **原本問題**：Jackson 讀取約 64 Ki 字元的本文時，會跨過預設字元分段邊界，反覆配置陣列、拼接字串。這些短命物件增加 CPU 與 GC 工作。先試過的文字串流讀法雖省配置，卻讓純文字解碼變慢，未採用。
2. **怎麼改善**：保留 Jackson 與既有 JSON 格式，只有 spool task 的讀取使用獨立、有界的 recycler。連續文字緩衝為 128 Ki 字元，容納預設 65,536 字元本文及截短標記；最多留一組閒置 recycler，每個保留的字元陣列不超過 128 Ki 字元、byte 陣列不超過 16 KiB。較大的資料仍可讀取，超大陣列不留下。共用 ObjectMapper 的設定、本文截短、候選規則去重、讀取容量門檻及交易流程沿用原行為。
3. **實測效果**：實際 SQLite spool 讀取，本文各 65,550 字元時，純文字／跳脫 JSON／中文的吞吐分別提高 76.0%／35.3%／19.0%，每筆 CPU 減少 43.5%／26.7%／15.9%，讀取執行緒配置量減少 59.7%／56.4%／43.2%。JMS 同程序交替測試約持平，詳見下表。十分鐘混合流量的 120,000 筆回應均正確，紀錄、備份及資料庫檢查正常；執行緒成長門檻未過。
4. **代價與限制**：通常多保留一個 256 KiB 的連續文字緩衝，閒置 recycler 的數量有界；同時使用中的 reader 各自持有緩衝。1 Ki 字元小本文速度持平，配置量增加約 88 bytes／筆（1.2%）。升級 Jackson 時須重驗其公開 recycler API。這是有限、少樣本的單機觀察，沒有證明永遠不會 OOM。JMS ACK、交易、重試與回覆流程沒有改動；實跑 Artemis，未實跑授權 TIBCO EMS。

## SQLite 讀取結果

每種版本兩個新 JVM，依舊／新／新／舊執行。表格為各輪平均，配置量只計讀取執行緒，CPU 計整個程序。

| 本文各欄 | 舊／新筆數每秒 | 每筆 CPU 降低 | 每筆配置量降低 |
|---|---:|---:|---:|
| 1,024 字元純文字 | 86,766／86,780 | 0.2% | **增加 1.2%** |
| 65,550 字元純文字 | 4,184／7,363 | 43.5% | 59.7% |
| 65,550 字元跳脫 JSON | 2,202／2,978 | 26.7% | 56.4% |
| 65,550 字元中文／emoji | 835／994 | 15.9% | 43.2% |

Linux、4 CPU 配額、JDK 17.0.20.1、G1、512 MiB heap、工作區 overlay 檔案系統。每組先寫入 50 筆，核對本文、時間及 headers，再暖機 3 秒、量測 5 秒，重複讀取同一批；每批讀取上限 32 MiB。request／response 本文相同，analysis body 與 request 去重，候選列表為空；這是熱資料讀取成本，不是持續寫入能力。首次測試錯把上限設為 16 MiB，中文批次只讀回 35 筆；該測試未納入，失敗原檔保留。

分支提供 `requestLogSpoolReadCost` Gradle 工作，可用 `./gradlew` 或 Windows 的 `.\gradlew.bat` 執行；`-PspoolReadCostOutput=artifacts/spool-read-cost` 可指定輸出。正式比較以同一份探針 JAR 經 PropertiesLauncher 載入兩個凍結的 Echo JAR，避免把不同探針當成產品差異。

## HTTP／JMS 對照與長跑

所有應用層比較使用 512 MiB heap、保留 10,000 筆、寫入上限 1,000／秒、128 KiB padding、真實 Artemis request/reply 與轉發；回應本文、狀態及 correlation 均核對。短測採同一份主資料庫 seed，各輪各啟新 JVM；高壓時非同步紀錄丟棄另列，回應成功不代表紀錄完整。

| 測法 | 舊／新平均筆數每秒 | 解讀 |
|---|---:|---|
| 四個新 JVM、JMS 模擬，5 秒內部暖機＋10 秒量測 | 303.4／208.9 | 新版較低 31.1%，不能略去 |
| 同組短測、JMS 轉發 | 100.1／94.0 | 新版較低 6.1% |
| 同組短測、HTTP 轉發 | 815.2／848.8 | 新版較高 4.1%，不能單獨作整體效能宣傳 |
| 較充分暖機、兩個新 JVM、JMS 模擬，含 JFR | 235.5／276.1 | 每版僅一個 JVM、各兩段 30 秒；方向反轉 |
| **同程序交替舊／新／新／舊，JMS 模擬** | **283.9／285.2** | **+0.4%，沒有一致的整體加速證據** |

充分暖機對照先送完 12,000 筆混合請求，再各測兩段；JFR 顯示主要 CPU 樣本仍在 Artemis／Netty 大訊息路徑，不能把樣本占比當成精確 CPU 用量。同程序測試使用外部測試啟動器，啟動後一次替換 reader 為切換包裝器，以 AtomicBoolean 選原本 generic ObjectMapper 或候選 reader；每段前排空紀錄，切換呼叫計數確認生效。正式程式沒有切換旗標或測試 API。每段內部暖機 5 秒、正式 20 秒、8 個 JMS caller；舊 P99 40.5–43.5 ms，新 39.0–43.6 ms，四段均零紀錄丟棄／未確認寫入。這隔離了程序重啟差異，但每種讀法仍只有兩段，不能推論所有負載。

高壓四 JVM 測試中，HTTP 正式視窗的紀錄丟棄舊版為 619／0、新版為 203／68；JMS 兩種情境皆為零。紀錄處理在 HTTP 視窗結束時仍有積壓，後續排空；不把回應吞吐當作紀錄寫入吞吐。不同階段的數字不合併計算。

十分鐘測試另用 8 個 paced caller，HTTP／JMS 各半：HTTP 固定、模板、轉發、延遲；JMS 模擬、轉發。暖機 6×20 秒後，正式完成 120,000 筆／600.106 秒；連暖機共落庫 144,000 筆，丟棄／重試／未確認寫入／JMS 失敗皆為零，最後排空。備份完成 7 次、清掉 5 份、失敗 0 次；主庫 `quick_check=ok`，保留 9,763 筆，GC 歷史過期清理有執行。

**原始長跑 `passed=false`**：七項資源成長檢查中六項通過，執行緒分鐘統計 184→189（+5）超過原定 +4 門檻，沒有放寬門檻或改寫原始結果。兩次 thread dump 的差異為 Artemis server worker 18→23（實際設定上限 30）、Artemis IO worker 5→8、HTTP worker 1→2（設定上限 32）；JMS listener 數相同。這支持既有執行緒池延後暖機的解釋，不能據此宣稱任意長度運行不會洩漏。正式流量沒有強制 GC；自然 GC 後 heap 的分鐘統計增加 5.68 MiB，結束排空／查詢後才做一次診斷 GC，heap 99.22 MiB、RSS 1,066.77 MiB。512 MiB heap 不等於整個程序只用 512 MiB。
