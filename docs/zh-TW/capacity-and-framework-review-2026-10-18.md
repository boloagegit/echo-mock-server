# 512 MiB 容量與 framework 成本檢視

[English](../capacity-and-framework-review-2026-10-18.md)

本輪改用大訊息驗證正式環境的保留量。SQLite 模式保留更多筆主要增加磁碟負擔；`-Xmx512m` 只限制 Java heap，並不限制整個程序為 512 MiB。本輪沒有更改正式環境的保留筆數、寫入限速或 JMS 語意。

建議先用**資料庫保留 10,000 筆、維持每秒 1,000 筆寫入上限**。20,000 筆也通過本次觀察，但這組主檔加兩份備份約需 7.4 GiB，備份中還需新快照／WAL／spool 空間；10k 混合組的磁碟量也不是每筆皆大本文的最壞預算。不限速是已測試的選項，沒有改成新預設，需依實際流量、延遲及磁碟能力選擇。512 MiB heap 下，實際整個程序 RSS 約 1.0–1.1 GiB。

## 大訊息承受能力

Linux／JDK 17／G1、四核心配額，heap 初始／上限皆 512 MiB；原生 HTTP 使用 2 個 I/O／32 個 worker，JMS concurrency 10–30。透過獨立 Artemis 下游 broker／兩個 consumer 真實轉發。輸入含 128 KiB padding，逐筆核對完整轉發本文與 JMS correlation ID。紀錄沿用原本每欄最多 **65,536 字元**加截短標記，觀察最大值為 65,550 字元；並非完整保留每欄 128 KiB。中文 UTF-8、更多 headers／規則分析等，不能直接套用相同空間估計。

資料庫放 workspace overlay 檔案系統，沒有使用 `/tmp` tmpfs。每兩分鐘備份、最多兩份／合計 8 GiB；housekeeping 刻意每秒執行，較正式預設每小時一次更密集。GC 歷史 60 秒到期。正式流量連續十分鐘，中途不要求 GC；最後停止流量、排空佇列、完成一般快照與預設查詢後，另外做一次診斷 Full GC，不混入自然 GC 成長判定。

|---|---:|---:|---:|---:|---:|
| 2,000 / 1,931 | 1,000 | 120,000 / 199.98 | 104.6 / 1050.7 | 144.3 | 6 / 4 / 0 |
| 10,000 / 9,777 | 不限速測試 | 120,000 / 199.97 | 106.5 / 1087.1 | 647.0 | 6 / 4 / 0 |
| 20,000 / 19,925 | 不限速測試 | 48,000 / 79.99 | 99.0 / 1013.0 | 2,517.5 | 9 / 7 / 0 |

備份／清理次數包含啟動、暖機與排空。

2,000／10,000 組為 HTTP／JMS 各半：HTTP 固定／模板／轉發／延遲各占四分之一，JMS 模擬／轉發各半。20,000 組全部為真實 JMS 轉發，request／response 紀錄皆達截短上限；負載種類與流量不同，不能把磁碟、記憶體或延遲差異都歸因於保留筆數。各組暖機至少寫入 24,000 筆，先填滿保留量再正式計時。批次清理預留空間，故實際保留筆數會略低於設定上限。

三組 ERROR／OOM、紀錄丟棄、未確認寫入、儲存重試與 JMS 失敗皆為零，結束佇列排空。七項成長門檻皆通過，但並非完全沒有增加。依保留量順序，自然 GC 後 heap 視窗差為 +6.39 / +5.63 / +11.00 MiB，RSS 為 +6.34 / +11.99 / +14.31 MiB；正式秒數為 600.056 / 600.085 / 600.040。結束時預設取全部摘要分別需 133.0 / 346.7 / 871.3 ms。

第一次全轉發要求每秒 200 筆，在暖機時停止：4,000 筆正確回應需 47.722 秒（83.82／秒），之後取樣約 95／秒。保留為取消結果，沒有正式驗收；每秒 80 筆重測通過不代表能承受 200 筆。

每分鐘查詢一次 50 筆分頁、單筆本文與流量統計；時間包含本機 HTTP 客戶端及 JSON 解析，不代表瀏覽器畫面時間。預設 `/api/admin/logs` 取全部保留的**摘要**，不載入全部本文。資料庫完整性核對通過。十分鐘與 Young GC 的觀察不能證明永久不洩漏；本輪也是資料庫模式，不能推論 20,000 筆放在 memory 模式安全。

## 修正持續寫入時備份可能卡住

1. **原本問題**：SQLite online backup 在其他連線提交後可能重新複製。第一輪 2,000 筆／128 KiB 混合測試，備份從 11:28 等到 11:38 停流量才完成。雖然 120,000 筆回應在 600.102 秒內皆正確、紀錄零丟棄，但備份／清理驗收失敗，保留這個失敗結果。
2. **怎麼改善**：在新借用的來源連線建立 `DEFERRED` 讀取快照，固定複製內容，WAL 寫入仍可繼續。複製後釋放快照、還原連線池設定；完整性驗證、發布及保留清理不變。
3. **實測效果**：持續寫入回歸測試在舊程式 15 秒逾時，修正後可在 writer 持續運作時完成。容量驗收各組都有流量中備份。完整 `check`／SpotBugs 通過：2,221 項測試、0 失敗、6 略過。[CI](https://github.com/boloagegit/echo-mock-server/actions/runs/39125026609) 通過 Linux JDK 17／21、Windows JDK 17 及 Docker。
4. **代價與限制**：讀取快照持有期間 WAL 可能暫時增加；慢磁碟仍會拉長複製／驗證時間，需要預留暫存空間。沒有修改 JMS ACK、交易、轉發與重連。未能取得合法 TIBCO EMS 環境，不能宣稱已驗證實際 EMS。

## 每秒寫入上限與保留筆數

原本預設每秒最多搬 1,000 筆到主紀錄資料庫。提高保留筆數是增加歷史長度；提高這個速率則增加背景 CPU／I/O。每秒總流量 200 筆時碰不到 1,000 上限，因此不能從低流量長測推論取消上限會加速。注意目前設 `0` 會被修正為 **1／秒**，不是取消；本輪用 `2147483647` 模擬不限速。

每輪新 JVM／512 MiB，相同保留量使用同一份 seed，128 KiB padding；JMS 八個 caller、HTTP 16 連線，各情境暖機五秒、正式十秒。只有這批峰值比較關備份。順序為 2k 限速、10k 不限速、20k 限速／不限速／不限速／限速、10k 限速、2k 不限速。20k 各設定兩個 JVM，其他各一個，只作探索；表格為各輪平均，不是合併百分位。

| 保留量 | 上限／秒 | JVM 數 | JMS 模擬／秒 | JMS 轉發／秒 | HTTP 轉發／秒 | HTTP 主 DB 寫入／秒 | 各 JVM 全階段丟棄 |
|---|---:|---:|---:|---:|---:|---:|---|
| 2,000 | 1,000 | 1 | 291.8 | 96.9 | 781.0 | 494.7 | 1880 |
| 2,000 | 不限速測試 | 1 | 196.4 | 98.0 | 795.4 | 564.0 | 1685 |
| 10,000 | 1,000 | 1 | 191.6 | 88.1 | 886.1 | 519.6 | 88 |
| 10,000 | 不限速測試 | 1 | 185.6 | 90.1 | 897.5 | 581.2 | 100 |
| 20,000 | 1,000 | 2 | 174.0 | 81.3 | 911.9 | 519.6 | 90, 112 |
| 20,000 | 不限速測試 | 2 | 282.1 | 101.8 | 870.8 | 637.1 | 0, 76 |

20k 不限速平均 JMS 轉發較高 25.2%、模擬較高 62.1%，HTTP 轉發反而低 4.5%。這些短測尚未隔離因果：JMS 流量未達 1,000／秒，JVM 有波動，各設定僅兩次。不是證明 JMS 被硬限為每秒 1,000，或所有情境都會加速。直接打下游的前／後 JMS 對照為 254.5／280.4 筆／秒，下游本身也有延遲。

20k 各輪 P99 平均（限速 → 不限速，ms）為 jms-mock 79.528 → 45.154; jms-forward 140.902 → 121.864; http-forward 54.428 → 57.534.

HTTP 寫入量以正式量測外層時間計算，可能含之前待寫資料；JMS 計數時間另包含五秒暖機及客戶端初始化。全階段丟棄含初始暖機、所有情境與排空，不能除以正式回應數當遺失率。收到的本文／correlation 皆正確，重試與未確認寫入為零。20k 的 HTTP 短測結束仍有 3,741–6,346 筆待寫，之後花 3.0–7.6 秒排空；十秒回應吞吐，即使當下零丟棄，也不是能永久完整寫入的容量。



另外獨立重建相同 HTTP 下游，暖機十五秒／正式十秒、16 連線，直接呼叫核對 7,318.7 筆／秒、零錯誤。與 Echo 開紀錄路徑相較，轉發／紀錄仍有明顯成本，不能只歸因於下游；實際吞吐不同，也不能直接相減 P99 拆解成本。

## Framework 負擔與後續優先順序

正式速度量測之外另跑 JMS JFR，共 1,737 個 execution samples；最接近頂端的可辨識 library frame 為 Artemis 988、Netty 572。可重疊 stack 計數為 Jackson 63、Hibernate 25、Spring bean lookup 7、Spring Data 3、AOP 1，不能相加當 CPU／wall-time 占比。突出路徑為 繼承的 `OutputStream.write` 迴圈 → `ClientLargeMessageImpl$ActiveMQOutputStream.write` → `ChannelBufferWrapper.writeByte`，後者有 823 個 leaf samples；配置採樣也指向 Jackson 文字／byte 緩衝。優先候選是 provider 大訊息批次複製與 spool 序列化配置，這輪尚未修改；Artemis 結果不能當成 TIBCO 結論。

局部查找探針為單一 JVM，各路徑暖機五秒，現有／直接／直接／現有各八秒；皆透過同一 live holder 每次取得新快照，確認候選內容相同與規則異動仍生效。比較包含整個 service 查找與直接 holder 存取，不只是單一 bean lookup。

| 查找 | 現有 ns／次 | 直接 holder ns／次 | 現有／直接呼叫執行緒配置 bytes／次 |
|---|---:|---:|---:|
| HTTP | 218.4 | 70.7 | 376 / 120 |
| JMS | 189.1 | 42.1 | 272 / 16 |

每次只省約 0.15 微秒／256 bytes，並非 HTTP／JMS 整體改善。另一個 ABBA 實驗使用真正 spool task、兩欄各 65,536 字元，確認輸出 bytes 相同及 JSON 來回內容正確。一般讀寫／預備 typed reader-writer 每次 encode/decode 平均 0.361／0.365 ms、配置 749.9／749.9 KiB，沒有觀察到改善，因此未更換 codec 或移除 framework。第一次探針誤要求 List 容器同一物件，保留該失敗；改為核對候選內容後重測通過。



前一份 [JPA／JDBC 寫入實驗](request-log-jdbc-experiment-2026-10-18.md) 只量主資料庫插入成本，不能把其中 47.2% 加到整台 Echo 的吞吐。原生 HTTP 已避開適用路徑的 MVC dispatch，規則快照已避免每筆查 DB，spool 也已實作本文去重。Spring JMS 可能重用 listener 的交易 session，不能假設每則訊息必定新建 session，或移除 annotation 就能避免整份本文轉換。

## 更新 WireMock HTTP 對照

Echo 使用 `ab7b292`（後續備份修正之前）對 WireMock OSS standalone 3.13.2；同 JDK 17／G1／1 GiB heap、四條規則、loopback HTTP/1.1、16 連線。八輪主要比較皆成功：關紀錄 E/W/W/E、開紀錄 W/E/E/W，各產品／模式兩個新 JVM。先以固定回應暖機 30 秒，各情境再暖機 5 秒、量測 15 秒。每筆收到的 status／body 均核對，socket／內容錯誤為零。表格為各輪平均，P99 是各輪 P99 平均而非合併樣本百分位。

| 情境 | 關紀錄：Echo／WireMock 筆／秒 | 關紀錄：Echo／WireMock P99 ms | 開紀錄：Echo／WireMock 筆／秒 |
|---|---:|---:|---:|
| fixed | 70,131 / 56,606 | 1.816 / 4.273 | 46,032 / 2,393 |
| template | 69,204 / 32,285 | 2.297 / 5.083 | 43,080 / 2,574 |
| xml16k | 29,924 / 21,847 | 7.823 / 5.735 | 17,655 / 2,772 |
| forward16k | 11,858 / 9,050 | 4.942 / 4.631 | 7,065 / 1,955 |

這幾組平均吞吐是 Echo 較高；XML 與轉發的 P99 則較差，不能宣稱所有指標皆勝。

開紀錄欄是**回應吞吐，不是完整寫入吞吐**：Echo 非同步 SQLite、每秒 1,000 上限，兩個完整執行分別回報丟棄 3,181,717／3,236,021 筆（保留跳過及交接丟棄）；WireMock 同步維護最多 10,000 筆的記憶體 journal，兩者保證不同。這批峰值比較的資料庫在 `/tmp` **tmpfs**，不能視為實體磁碟效能。

四個情境／排空後的 RSS 平均（MiB），關紀錄為 Echo／WireMock 1159.7／822.1，開紀錄為 1233.3／1216.9。這是不同實際吞吐下的短測結束快照，不是同流量長期記憶體基準；兩組都不是 Echo 較省。

另外一輪 Echo memory 模式飽和測試，在暖機發生 1,357,254／1,390,004 筆回應核對失敗，為現有佇列滿回 503 的行為，不是有效速度結果。因此整份比較腳本並非全部通過，成功的是八輪主要比較。原訂對等十分鐘 HTTP 記憶體重測，因需求轉為 512 MiB／大訊息而在正式流量前取消；[前一份成對記憶體與穩定性觀察](wiremock-comparison-2026-10-18.md) 需獨立看待，本輪沒有新的對等長跑結果。WireMock OSS 也沒有 JMS 對應功能。
